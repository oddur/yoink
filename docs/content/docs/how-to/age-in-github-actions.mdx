A CI workflow needs one environment variable, `YOINK_AGE_KEY`, to use age-sealed secrets. For the keypair model (recipient and identity), see [Secrets](/docs/explanation/secrets#sealed-secrets-age).

## Prerequisites

Sealed secrets work on your laptop. If they do not, do the [one-time setup](/docs/how-to/sealed-secrets-workflow#one-time-setup) first. Make sure that:

- `secrets.age` is committed to the repo.
- `secrets.recipients:` in `yoink.yaml` contains the recipient of your laptop.
- yoink can read the identity of your laptop. The default location is `~/.config/yoink/keys/<recipient>.key`.

## Setup

### Generate a CI-only identity and ship it to GitHub [step]

**Do not use the laptop keypair for CI.** Give CI its own keypair. If a CI runner is compromised, you can then revoke its identity and your daily work continues.

```sh
yoink secrets key generate --print | gh secret set YOINK_AGE_KEY --repo you/your-repo
```

`--print` sends only the `AGE-SECRET-KEY-1…` line to **stdout**, so `gh secret set` gets only the key. The recipient (`age1…`) goes to **stderr** and stays on the terminal. You copy the recipient into `yoink.yaml` in the next step.

To paste the key manually, run the command without the pipe and copy the secret. Create a secret with the name `YOINK_AGE_KEY` at `Repo Settings → Secrets and variables → Actions → New repository secret`. Then clear the scrollback with `reset`, because the identity is still in your terminal.

### Add the CI recipient to `yoink.yaml` [step]

Add the CI recipient to the `recipients:` list. Do not replace the laptop recipient. If you replace it, your laptop cannot open the file after the next seal. Each identity in the list decrypts the same `secrets.age`.

```yaml
secrets:
  provider: age
  recipients:
    - age1...your-laptop-recipient                                    # already there
    - age1w8jcq22re378p38nxrudmjqdkyh42cyzsge7snwzqxlzyqt7fgkqmmvy45  # CI
```

Seal the file again so that the two identities can decrypt:

```sh
yoink secrets seal < /dev/null   # no value changes, seals against the new recipient list
git add yoink.yaml secrets.age
git commit -m "chore: add CI to age recipients"
git push
```

### Wire it into the workflow [step]

```yaml
# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [live]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install yoink
        run: |
          curl -LsSf https://github.com/oddur/yoink/releases/latest/download/yoink-installer.sh | sh
          echo "$HOME/.cargo/bin" >> $GITHUB_PATH

      - name: Deploy
        run: yoink up --tag api=${{ github.sha }} --tag web=${{ github.sha }}
        env:
          YOINK_AGE_KEY: ${{ secrets.YOINK_AGE_KEY }}
```

yoink reads `YOINK_AGE_KEY` from the environment and decrypts `secrets.age` on the runner. The key lookup is the same locally and in CI. For the sequence of sources, see [Identity resolution](/docs/explanation/secrets#identity-resolution). If no source has a key, yoink stops with an error that names `YOINK_AGE_KEY` and `YOINK_AGE_KEY_FILE`.

## Rotating the CI key

Rotate the CI identity when a person with access leaves, when you suspect a leak, or when your schedule requires it.

### Run `yoink secrets rotate` [step]

```sh
yoink secrets rotate
```

The command generates a new identity and seals `secrets.age` again against the old recipients plus the new recipient. It prints the new identity to stdout and the new recipient to stderr. The command does not change `yoink.yaml`. Add the new recipient to `secrets.recipients:`. Then commit `yoink.yaml` and `secrets.age`.

### Update the `YOINK_AGE_KEY` GitHub secret [step]

Set the secret to the new identity that the rotate command printed.

### Make sure that CI decrypts with the new key [step]

Push, and monitor a deploy run. During the transition, the old and the new identity decrypt. Thus a runner that still has the old key does not cause a deploy failure.

### Remove the old recipient [step]

When CI decrypts correctly, remove the old recipient from `yoink.yaml`. Then run `yoink secrets seal < /dev/null`. This seals the file against the remaining recipients only. Commit the change.

<Callout type="warn">

**After a leak, rotate the recipients and the values.** Remove the leaked recipient, so that the leaked identity cannot decrypt new edits. Rotate every value, because the leaked identity decrypts each old copy of `secrets.age`. For the full procedure, see [Compromised key: emergency rotation](/docs/how-to/sealed-secrets-workflow#compromised-key-emergency-rotation).

</Callout>

## Show the sealed keys without their values

To make sure that CI can read the keys that you expect, add this step to a debug run:

```yaml
- name: List sealed keys
  run: yoink secrets show       # masked by default
  env:
    YOINK_AGE_KEY: ${{ secrets.YOINK_AGE_KEY }}
```

`show --reveal` prints the values. Do not use `--reveal` in CI, because each person with read access to the repo can read the workflow logs. yoink refuses `--reveal` when `$CI` or a similar CI variable is set. `YOINK_ALLOW_REVEAL_IN_CI=1` overrides the refusal, for example when you pipe the values into a different secret store.

## Failure modes

| Symptom | Cause | Correction |
|---|---|---|
| `age decryption failed` | The key in the GitHub secret does not match a recipient of `secrets.age`. You did not update the GitHub secret after a rotation, or you did not seal the file again after you added the recipient. | Run `yoink secrets show` locally with the same key to find which cause applies. |
| `no matching age identity found` | The deploy step has no `env: YOINK_AGE_KEY:` block. | Add the block to the step. |
| The workflow logs contain secret values | A step printed them. GitHub masks only registered secrets, and the plaintext that yoink decrypts is not registered. | Do not use `yoink secrets show --reveal` in CI. Do not run `echo $DATABASE_URL` in a step. |
