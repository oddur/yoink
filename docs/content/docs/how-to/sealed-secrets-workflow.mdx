These tasks apply to `provider: age`. For the keypair model and the threat model, see [Secrets](/docs/explanation/secrets).

## One-time setup

`yoink init` generates an identity at `~/.config/yoink/keys/<recipient>.key` and adds the `secrets:` block to `yoink.yaml`. If you ran `yoink init`, go to [Sealing values](#sealing-values). If you did not, do these steps.

### Generate a keypair [step]

```sh
yoink secrets key generate
```

The command writes a new identity to `~/.config/yoink/keys/<recipient>.key` with mode 0600. It prints the matching **recipient**, which is the public half (`age1…`). The file name is the recipient, so one directory holds the identities of many projects. yoink selects the correct key for each `yoink.yaml`. An environment variable or a gitignore entry is not necessary.

If you lose the key, you cannot recover the values that are sealed against it. Make a backup with one or more of these methods:

- Password manager: paste the output of `cat ~/.config/yoink/keys/<recipient>.key` into 1Password, Bitwarden, or Keychain.
- Encrypted backup: run `cp ~/.config/yoink/keys/<recipient>.key ~/Backups/`.
- Second identity: add the `age1…` recipient of a teammate to `yoink.yaml`. Then a second identity can also unseal.

### Add the recipient to `yoink.yaml` [step]

```yaml
secrets:
  provider: age
  recipients:
    - age1w8jcq22re378p38nxrudmjqdkyh42cyzsge7snwzqxlzyqt7fgkqmmvy45
```

The recipient is safe to commit. `yoink secrets key public` derives it again from your current identity.

Then seal the first values with the procedure in [Sealing values](#sealing-values). That procedure creates `secrets.age`. Commit this file.

## Routing the identity to a managed store

To keep the identity in a managed store and not in the keys directory, pipe `key generate --print` into the store. With `--print`, only the `AGE-SECRET-KEY-1…` line goes to **stdout**. The header, the recipient, and the instructions go to **stderr**.

```sh
# GitHub Actions
yoink secrets key generate --print | gh secret set YOINK_AGE_KEY --repo you/your-repo

# 1Password
yoink secrets key generate --print | op item create --category=password \
  --title='yoink: your-repo' --vault=Engineering password=-

# AWS Secrets Manager
yoink secrets key generate --print | aws secretsmanager create-secret \
  --name yoink/your-repo --secret-string file:///dev/stdin

# macOS Keychain
yoink secrets key generate --print | security add-generic-password \
  -s yoink-your-repo -a $USER -w
```

The recipient stays on the terminal. Copy it into `yoink.yaml`.

<Callout type="warn">

**Do not run `key generate --print` without a pipe.** Shell scrollback, iTerm shared sessions, and tmux capture-pane history keep the identity. Without `--print`, the command writes the identity to disk and writes nothing to stdout.

</Callout>

`--out PATH` writes the identity to a file of your choice with mode 0600, for example adjacent to `yoink.yaml`. yoink does not find this file automatically. Add the file to `.gitignore`. Then set `YOINK_AGE_KEY_FILE` to its path.

For the full CI procedure, see [AGE secrets in GitHub Actions](/docs/how-to/age-in-github-actions).

## Sealing values

```sh
yoink secrets edit
```

The command decrypts `secrets.age` and opens it in `$EDITOR` as a plain dotenv file. If `secrets.age` does not exist, the command starts a new file.

```dotenv
DATABASE_URL=postgres://user:pass@db.internal/app
JWT_SIGNING_KEY=...
GHCR_TOKEN=ghp_...
```

Save the file and close the editor. yoink makes sure that the dotenv is valid and seals it against the recipients in `yoink.yaml`. Then yoink writes `secrets.age` atomically. Commit and push the file. If you save without changes, yoink does not write the file.

To seal values without the editor, use `yoink secrets seal`:

```sh
echo "FOO=bar" | yoink secrets seal
yoink secrets seal --in plain.env
yoink secrets seal --as DEPLOY_KEY=@/tmp/deploy_key   # single key from a file
yoink secrets seal --as YOINK_DOCS_HOST=5.75.123.45 \
                   --as CF_ORIGIN_CERT=@cert.pem \
                   --as CF_ORIGIN_KEY=@key.pem        # multiple in one shot
```

By default, `secrets seal` **merges into the existing bundle**. It adds new keys, updates the keys that already exist, and keeps the other keys. The output shows the number of added, updated, and preserved keys. `--replace` writes a bundle that contains only the input keys. If `--replace` removes existing keys, yoink asks for confirmation. `--yes` skips the prompt.

After you change `secrets.recipients:`, seal the same values against the new list:

```sh
yoink secrets seal < /dev/null
```

The command merges an empty input. It changes no value and writes `secrets.age` for the current recipients.

To change one key during incident response, use the secrets pane of the TUI (`e` from any view). The pane shows, adds, edits, and removes one key at a time. For bulk edits, use `yoink secrets edit`.

## Using the values

Refer to each key by name from a service:

```yaml
services:
  - name: api
    image: ghcr.io/you/api
    secrets: [DATABASE_URL, JWT_SIGNING_KEY]
    env_from_secrets:
      OTEL_EXPORTER_OTLP_HEADERS: GRAFANA_AUTH_HEADER
```

yoink resolves the values from the sealed bundle and injects them as environment variables. The injected values are part of [`spec_hash`](/docs/explanation/architecture#drift-detection). Thus a changed value redeploys each service that refers to its key, as a config change does. `yoink up --dry-run` shows the diff before the deploy.

## Loading into a local dev shell

```sh
source <(yoink secrets env)                  # exports every key into the current shell
eval "$(yoink secrets env)"                  # equivalent for shells without process substitution
yoink secrets env --no-export > .env.local   # bare KEY='value' for `docker run --env-file` etc.
```

yoink escapes the values with POSIX single quotes. Thus `$`, embedded quotes, and newlines stay literal. If `$CI`, `$GITHUB_ACTIONS`, or a similar CI variable is set, the command refuses to run unless `YOINK_ALLOW_REVEAL_IN_CI=1` is set.

## Use the bundle from Terraform / CI

A profile in `yoink.yaml` defines the environment variables that one downstream tool needs. The same profile supplies your shell, your CI workflow, and a yoink pre-deploy hook. Thus the mapping from bundle key to env var name is in one place.

```yaml
# deploy-prod/yoink.yaml
secrets:
  provider: age
  recipients: [age1…]
  profiles:
    terraform-cloudflare:
      include: [CLOUDFLARE_API_TOKEN,
                TFSTATE_B2_KEY_ID, TFSTATE_B2_APPLICATION_KEY]
      rename:
        TFSTATE_B2_KEY_ID:          AWS_ACCESS_KEY_ID
        TFSTATE_B2_APPLICATION_KEY: AWS_SECRET_ACCESS_KEY
      unset: [B2_ENDPOINT, B2_BUCKET_NAME]
```

You can use `include`, `rename`, and `unset` together. For the schema, see [Secrets profiles](/docs/reference/config#secrets-profiles).

### From a Taskfile

```yaml
env:
  YOINK_TF:
    sh: cd ../../deploy-prod && yoink secrets env --profile terraform-cloudflare

tasks:
  tf:plan:
    cmds:
      - eval "$YOINK_TF" && terraform plan
```

One `yoink secrets env --profile …` command replaces an extractor block for each key.

### From a GitHub Actions workflow

```yaml
- run: |
    eval "$(cd deploy-prod && ../yoink-bin/yoink secrets env --profile terraform-cloudflare)"
    {
      echo "CLOUDFLARE_API_TOKEN=$CLOUDFLARE_API_TOKEN"
      echo "AWS_ACCESS_KEY_ID=$AWS_ACCESS_KEY_ID"
      echo "AWS_SECRET_ACCESS_KEY=$AWS_SECRET_ACCESS_KEY"
    } >> "$GITHUB_ENV"
  env:
    YOINK_ALLOW_REVEAL_IN_CI: "1"   # `secrets env` refuses to run in CI without this
```

`secrets env` refuses to run in CI unless `YOINK_ALLOW_REVEAL_IN_CI=1` is set. When `$GITHUB_ENV` is set, yoink adds `echo '::add-mask::<value>'` for every revealed value before the exports. Thus every key gets a mask, and a mask line for each key is not necessary.

### From a yoink pre-deploy hook

A pre-deploy hook with `secrets_profile: <NAME>` applies the same profile in every `yoink up`. Subprocess hooks (hooks without `image:` or `tag:`) run `cmd[0]` directly on your computer and inherit the parent environment. Thus the `unset:` list of the profile applies as it does in your shell. A container hook rejects a profile that has an `unset:` list. For a full example, see [Run Terraform from a hook](/docs/how-to/terraform-from-hooks).

## Multiple environments (staging / prod)

To keep staging and prod values separate, give each environment its own config file, sealed file, and identity.

```
yoink.staging.yaml   secrets.staging.age   YOINK_AGE_KEY (in staging CI)
yoink.prod.yaml      secrets.prod.age      YOINK_AGE_KEY (in prod CI)
```

Give each YAML file its own `secrets.recipients:` and `secrets.file:`. Give each CI workflow only the identity of its environment. The two files use different recipients, so a leaked staging identity cannot decrypt the prod file.

If staging and prod share values (the same image and only a different `DATABASE_URL`), put the two recipients on one sealed file. Then each identity decrypts the file, and a compromise of one identity reveals the two environments. Deploys get environment-specific overrides from `--tag` or from a per-host YAML file.

## Backup and recovery

The sealed file is in git. The identity is the part that you cannot replace.

- **Keep the identity in two stores that cannot fail together.** Keep the primary copy in your secret manager. Keep the recovery copy offline: a sealed envelope, an encrypted USB drive, or a second manager under a different account. Do not put the two copies under one SSO.
- **Do a recovery test each quarter.** Decrypt `secrets.age` on a clean computer with only the recovery key.
- **Rotation is not a backup.** Rotation needs the current identity. If you lose the two copies, seal all values again from the upstream sources (Stripe dashboard, AWS console, manager CLIs).

## Planned key rotation

```sh
yoink secrets rotate
```

The command generates a new identity and seals `secrets.age` again against the existing recipients plus the new recipient. It prints the new identity to stdout and the new recipient to stderr. It does not write the identity to disk, and it does not change `yoink.yaml`. The old and the new identity decrypt during the transition, so there is no deploy outage.

Then do these actions in this sequence:

1. Add the new recipient to `secrets.recipients:` in `yoink.yaml`. If you do not, the next `secrets edit` or `secrets seal` removes the new recipient from the sealed file.
2. Put the new identity into CI (`YOINK_AGE_KEY`) and into your secret manager.
3. Commit `yoink.yaml` and `secrets.age`.
4. Run one `yoink up` with *only* the new identity in `YOINK_AGE_KEY`. Make sure that the deploy log has no `age decryption failed` error.
5. Remove the old recipient from `yoink.yaml`.
6. Run `yoink secrets seal < /dev/null`. This removes the old recipient from the sealed file.
7. Commit the change. Then remove the old identity from your manager.

If you do steps 5 and 6 before step 4 succeeds, each teammate or CI runner that still uses the old key cannot decrypt.

To rotate without `yoink secrets rotate`, do these steps.

### Generate a new identity [step]

```sh
yoink secrets key generate
```

The command writes the identity to `~/.config/yoink/keys/<new-recipient>.key` and prints the recipient.

### Add the new recipient alongside the old one [step]

```yaml
secrets:
  recipients:
    - age1...old
    - age1...new
```

### Re-seal against both [step]

```sh
yoink secrets seal < /dev/null   # no value changes, seals against the two recipients
git commit -am 'rotate age recipient'
```

### Update CI to the new private key [step]

Run `gh secret set YOINK_AGE_KEY` (or the equivalent command for your store) with the new identity. Use `--print` to pipe only the identity.

### Run a deploy with only the new key [step]

Make sure that the deploy succeeds before you remove the old recipient.

### Remove the old recipient [step]

Remove the old recipient from `secrets.recipients:`. Run `yoink secrets seal < /dev/null` again. Commit the change. Then remove the old key from your manager.

## Compromised key: emergency rotation

If `YOINK_AGE_KEY` leaks, rotate **today**. Examples of a leak are a paste into Slack, a workflow log, a stolen unlocked laptop, and the password manager of a terminated employee. The leaked key decrypts every value sealed against it for as long as the attacker has the repo.

### Generate a new identity, re-seal, ship [step]

Do the full procedure in [Planned key rotation](#planned-key-rotation), which includes the removal of the old recipient. After that, the leaked identity cannot decrypt new revisions.

### Rotate every value in the bundle, not only the key [step]

The attacker can decrypt each old revision of `secrets.age`. The yoink rotation replaces the wrapping key, not the contents. Change the database password. Generate a new JWT signing key. Rotate the GHCR token. Then seal the new values.

### Revoke cached copies of the old key [step]

- GitHub Actions secret: remove the secret and create it again with the new key.
- 1Password or vault entries: remove the old version. Some managers keep the edit history.
- Key files on a laptop: remove them with `srm` or `shred`.

### Audit the deploy log [step]

`git log secrets.age` shows the edits to the file. `gh run list --workflow=deploy.yml` shows the deploys that used the key. If the leak window contains deploys that you do not know, treat the host as compromised.
