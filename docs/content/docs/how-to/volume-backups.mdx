[restic](https://restic.net/) runs as a yoink-managed service and makes nightly off-host backups of the docker volumes. The repo is on any S3-compatible object storage: Hetzner Object Storage, Backblaze B2, AWS S3, MinIO, Wasabi, Vultr, or a self-hosted [RustFS](https://rustfs.com/). You supply the bucket, the S3 keys, and a repo password. The bundled templates supply the remaining config.

For the design of the backup service, see [How volume backups work](/docs/explanation/volume-backups).

## Back up volumes to an S3 bucket

### Provision a bucket and S3 keys at your storage provider [step]

Do this one time, outside yoink. For a self-hosted RustFS backend, see [Self-hosted backend](#self-hosted-backend-rustfs-over-tailscale).

### Generate the backup service from the bundled template [step]

```sh
yoink add restic-backups \
  --var "repository=s3:https://s3.example.com/MY-BUCKET" \
  --var "schedule=0 30 3 * * *" \
  --var "retention=--keep-daily 7 --keep-weekly 4 --keep-monthly 6"
```

### Seal the S3 keys [step]

The template generates no secrets. Seal the S3 keys and a `RESTIC_PASSWORD` that you make, for example with `openssl rand -base64 48`.

```sh
yoink secrets edit
#    RESTIC_PASSWORD=…
#    S3_ACCESS_KEY_ID=…
#    S3_SECRET_ACCESS_KEY=…
```

Keep a copy of `RESTIC_PASSWORD` in a durable place. Without it, you cannot decrypt the backups.

### List the volumes for backup, then deploy [step]

Edit `services/backups.yaml`. Under `run.volumes:`, add one read-only mount for each volume, as the commented examples show. Then deploy:

```sh
yoink up
```

After the next cron tick, `restic snapshots` lists the first backup. The default schedule is `0 30 3 * * *`, which is 03:30 UTC.

## Self-hosted backend (RustFS over Tailscale)

[RustFS](https://rustfs.com/) is an S3-compatible object storage with an Apache-2.0 license. A RustFS instance on a separate host on the tailnet needs no third-party storage provider and has no egress charges. The `rustfs` template generates the service.

### Deploy RustFS on the off-site host [step]

Make sure that the host is in the `hosts:` list and that it is reachable over the tailnet.

```sh
yoink add rustfs --var "bind_address=100.64.1.5"   # the host's tailnet IP
```

Edit `services/rustfs.yaml`. Add `hosts: [vault-host.tailnet]`, so that RustFS deploys only on the off-site host. Do the next step before you run `yoink up`.

### Create the data volume with the correct ownership [step]

RustFS runs as uid 10001. Before the first deploy, create the data volume and change its owner, so that the daemon can write to it.

```sh
ssh root@<vault-host> '
  docker volume create rustfs-rustfs-data
  chown -R 10001:10001 /var/lib/docker/volumes/rustfs-rustfs-data/_data
'
```

Then run `yoink up`.

### Create the backup bucket [step]

restic creates the repo metadata in a bucket, but it does not create the bucket. After RustFS starts, create the bucket with any S3 client:

```sh
ssh root@<vault-host> "docker run --rm --network=<your-network> \
  -e AWS_ACCESS_KEY_ID='$(yoink secrets show --reveal | grep '^RUSTFS_ACCESS_KEY=' | cut -d= -f2-)' \
  -e AWS_SECRET_ACCESS_KEY='$(yoink secrets show --reveal | grep '^RUSTFS_SECRET_KEY=' | cut -d= -f2-)' \
  -e AWS_REGION=us-east-1 \
  amazon/aws-cli --endpoint-url=http://rustfs:9000 s3 mb s3://backups"
```

### Generate the backups service for the RustFS endpoint [step]

```sh
yoink add restic-backups \
  --var "repository=s3:http://rustfs-vault.tailnet:9000/backups"
```

### Use the RustFS credentials as the S3 keys [step]

The generated `RUSTFS_ACCESS_KEY` and `RUSTFS_SECRET_KEY` are the S3 root credentials of that RustFS instance. Copy them into `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`, which `restic-backups` reads. Also add a `RESTIC_PASSWORD`.

```sh
yoink secrets edit
#  S3_ACCESS_KEY_ID    <- the RUSTFS_ACCESS_KEY value from `yoink secrets show --reveal`
#  S3_SECRET_ACCESS_KEY <- the RUSTFS_SECRET_KEY value from `yoink secrets show --reveal`
#  RESTIC_PASSWORD=…
```

### Deploy [step]

List the volumes in `services/backups.yaml`, as in the S3 procedure. Then run `yoink up`. For the tailnet hostname conventions, see [Networking](/docs/explanation/networking).

## Serve a bucket as public HTTPS through Caddy

A bucket policy can make one RustFS bucket anonymous-read. Then the bundled Caddy can serve the bucket as a public asset endpoint.

<Callout type="warn">

Use this procedure only for assets that are public. The bucket policy is the only access control on objects under `public-assets/*`.

</Callout>

### Make one bucket world-readable [step]

The policy gives access to objects only, not to the bucket listing. Run the command from any host on the same docker network.

```sh
POLICY='{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":"*","Action":"s3:GetObject","Resource":"arn:aws:s3:::public-assets/*"}]}'
docker run --rm --network=<your-network> \
  -e AWS_ACCESS_KEY_ID="$(yoink secrets show --reveal | grep '^RUSTFS_ACCESS_KEY=' | cut -d= -f2-)" \
  -e AWS_SECRET_ACCESS_KEY="$(yoink secrets show --reveal | grep '^RUSTFS_SECRET_KEY=' | cut -d= -f2-)" \
  -e AWS_REGION=us-east-1 \
  amazon/aws-cli --endpoint-url=http://rustfs:9000 s3api put-bucket-policy \
    --bucket public-assets --policy "$POLICY"
```

### Add a `domain:` and Caddy rewrite to `services/rustfs.yaml` [step]

```yaml
domain: assets.example.com
caddy_extra_caddyfile: |
  rewrite * /public-assets{path}
```

The rewrite adds the bucket prefix: `/foo.png` at the public domain maps to `/public-assets/foo.png` on RustFS. Because `domain:` is set, yoink generates the `reverse_proxy rustfs:9000` directive that proxies the rewritten path.

### Deploy and request the public domain [step]

Run `yoink up`. Then `https://assets.example.com/foo.png` serves the object from the `public-assets` bucket.

The path rewrite limits the public endpoint to one bucket. The other buckets and the admin API of the S3 endpoint stay internal. To reject PUT attempts at the proxy, add a method matcher: `@get method GET HEAD`, and `respond 405` for all other methods.

TLS comes from Let's Encrypt by default. For sealed origin certs, see [Cloudflare origin certs](/docs/how-to/cloudflare-origin-certs).

## PostgreSQL: point-in-time recovery via WAL archiving

A nightly snapshot loses all changes after the snapshot time. WAL archiving sends each write-ahead log segment to S3, and PostgreSQL replays the segments on a base backup. The `postgres` template generates this config when `wal_archiving=true`. For what the template generates, see [How volume backups work](/docs/explanation/volume-backups#postgresql-wal-archiving).

### Provision a WAL bucket [step]

Create the bucket before postgres starts to archive. `archive_command` does not create the bucket.

### Seal the S3 keys [step]

The WAL upload is an `aws s3 cp` command that reads the same two keys as `restic-backups`. If you sealed the keys for `restic-backups`, skip this step.

```sh
yoink secrets edit
#   S3_ACCESS_KEY_ID=…
#   S3_SECRET_ACCESS_KEY=…
```

### Generate postgres with WAL archiving on [step]

```sh
yoink add postgres \
  --var wal_archiving=true \
  --var wal_repository=s3://wal-archive \
  --var wal_endpoint=http://rustfs:9000   # omit for AWS S3
```

### Add the data volume to restic-backups [step]

Mount the postgres data volume read-only into the backups service. The restic snapshot of this volume is the base backup for point-in-time recovery.

```yaml
# services/backups.yaml
- pgdata-postgres:/data/pgdata-postgres:ro
```

### Keep the WAL archive as long as the oldest snapshot [step]

yoink does not remove old WAL segments. Remove the segments that are older than the oldest restic snapshot with `aws s3 rm`, or with RustFS lifecycle rules. Do not remove newer segments.

## Restore PostgreSQL to a point in time

This procedure is manual: yoink does not do it. The [PostgreSQL continuous archiving docs](https://www.postgresql.org/docs/current/continuous-archiving.html) give the full mechanics.

### Restore the latest pre-incident base snapshot [step]

Use `restic restore` to restore the latest pre-incident snapshot of `pgdata-postgres` to a fresh volume.

### Point `restore_command` at the WAL archive [step]

Add a `recovery.signal` file and a `restore_command` to the recovered data dir. The `.gz` suffix and `gunzip` match the compression on the archive side:

```
restore_command = 'aws s3 cp s3://wal-archive/%f.gz - | gunzip -c > %p'
```

### Set the recovery target and start postgres [step]

Set `recovery_target_time` to the moment that you want. Start postgres. Wait until the replay is complete.

## Make sure that the backups run

### Read the schedule log of go-cron [step]

```sh
yoink up
yoink logs backups -f
```

The log shows the next scheduled run of go-cron.

To force a snapshot immediately, uncomment `RUN_ON_STARTUP: "true"` in `services/backups.yaml` and deploy again. After the snapshot is complete, comment the line again.

### List snapshots from your laptop [step]

Run restic with the same secrets and the same repo URL:

```sh
docker run --rm \
  -e RESTIC_REPOSITORY="s3:https://s3.example.com/MY-BUCKET" \
  -e RESTIC_PASSWORD="$(yoink secrets show --reveal | grep '^RESTIC_PASSWORD=' | cut -d= -f2-)" \
  -e AWS_ACCESS_KEY_ID="$(yoink secrets show --reveal | grep '^S3_ACCESS_KEY_ID=' | cut -d= -f2-)" \
  -e AWS_SECRET_ACCESS_KEY="$(yoink secrets show --reveal | grep '^S3_SECRET_ACCESS_KEY=' | cut -d= -f2-)" \
  mazzolino/restic:1.8.2 \
  restic snapshots
```

## Restore

Run `restic restore` and `restic mount` (FUSE browsing) as one-off `docker run` commands with the same `mazzolino/restic` image. Pass the same env vars as in [List snapshots from your laptop](#list-snapshots-from-your-laptop). For `restic mount`, also pass `--device /dev/fuse --cap-add SYS_ADMIN`. The [restic docs](https://restic.readthedocs.io/en/stable/050_restore.html) give the full restore syntax.

For a long-lived FUSE service, see the `devices:` and `cap_add:` config in [hardware passthrough](/docs/how-to/hardware-passthrough#fuse-juicefs-sshfs-restic-mount).

## Troubleshooting

**`Fatal: unable to open repository at s3:…`**

The repo does not exist yet. The first `restic backup` initializes it. Wait for the first cron tick, or set `RUN_ON_STARTUP=true`. If the error continues, the `RESTIC_REPOSITORY` URL is wrong, or the S3 keys do not have read and write access to the bucket.

**`restic` panics with `signal: terminated` during a redeploy.**

The `drain_timeout` (`60s` in the generated service) was too short for an in-flight backup to stop cleanly. Increase `drain_timeout` in `services/backups.yaml`, or deploy outside the backup window.
